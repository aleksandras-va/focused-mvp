# Structure

Onion layering. Dependencies point inward, never back out.

```
src/
  app/            Next.js App Router: pages, layouts, Server Actions, Route Handlers
  components/     presentational components; ui/ is shadcn, vendored
  services/       use cases; the only layer app/ may import
  repositories/   every database query
  db/             connection, generated types
scripts/          operational scripts run with plain node (.mts)
```

## Layers

### `src/db/` — database management

The Kysely client and the generated schema types. Nothing about the business belongs
here.

- `index.ts` — the singleton Kysely instance. Import as `import { db } from "@/db"`.
  Pooled and cached on `globalThis` so dev hot reloads do not leak connections.
- `types.ts` — generated by kysely-codegen from the live database. Never edit.
  Regenerated automatically after every migrate and rollback.
- `tables.ts` — readable aliases over the generated types (`GearModel`, `Brand`,
  `CameraSpec`). Row shapes, not domain objects.
Schema changes are **not** made from this repo. They are handed over as plain SQL,
run by hand against the database, and picked up by `pnpm db:codegen`. The files in
`migrations/` are the historical record of how the current schema was built; nothing
new is added there.

### `src/repositories/` — data access

One file per aggregate, named `<thing>-repository.ts`. Repositories own all SQL,
speak the schema's snake_case, and return row shapes. Nothing outside this folder
imports `db` or writes a query.

Current: `model-repository.ts`, `brand-repository.ts`, `mount-repository.ts`,
`user-repository.ts`, `session-repository.ts`.

### `src/services/` — use cases

Named `<area>-service.ts`. Services compose repositories and map rows to camelCase
DTOs, so a column rename stops here instead of reaching a component. Derived values
(`isZoom`, formatted prices) are computed at this boundary.

Current: `catalog-service.ts`, `auth-service.ts`.

`auth-service.ts` reads and writes the session cookie directly, which is what the
Next.js data-security guide recommends for a data access layer.

### `src/components/` — presentation

`ui/` holds shadcn components, added with `pnpm shadcn add <name>` and treated as
vendored: excluded from Biome, edited only when the design demands it. Everything
beside it is app-specific composition (`site-header.tsx`, `listing-card.tsx`) that
takes data as props and never calls a service or a repository.

### `src/app/` — delivery

Server Components, Server Actions, and Route Handlers. They call **services** only —
never a repository, never `db`.

## Rules of thumb

- Every module in `db/`, `repositories/`, and `services/` starts with `import "server-only"`.
- A new query means a repository function, not a query inline in a page.
- A new page needs a service function, even a thin one, rather than a repository call.
- Ranking scores, join aliases, and other query mechanics stay inside the repository.

## Schema

The catalog is the product's edge: sellers pick a canonical model instead of typing
free text, so search is exact and specs are pre-filled.

- `brands`, `mounts` — lookups. A mount's `brand_id` is null when no single brand owns
  it (Micro Four Thirds, L-Mount).
- `models` — one row per real product ("X-T3"). `mount_id` is null for fixed-lens
  cameras. Unique on `(brand_id, name, mount_id) NULLS NOT DISTINCT`, because Sigma and
  Tamron ship identically-named lenses per mount.
- `camera_specs`, `lens_specs` — one-to-one detail per category, so an ad needs only a
  single `model_id` foreign key.
- `model_aliases` — every spelling that should resolve to a model. `normalized` is a
  generated column (lowercase, non-alphanumerics stripped), so "Fuji XT3", "X-T3", and
  "fujifilm x t3" collapse to one lookup key. Exactly one alias per model carries
  `is_canonical`; that is the display name.

Search ranks exact alias matches first, then prefixes, then `pg_trgm` similarity for
real typos.

### Accounts

- `users` — email, display name, and `seller_type` (`private` or `store`). Store fields
  are all-or-nothing, enforced by a check constraint.
- `sessions` — database-backed, referenced by an httpOnly cookie. Placeholder auth: no
  passwords, so an unknown email creates an account. Replace before any real traffic.
